                              1. OVERVIEW
================================================================================

This document analyzes the complete flow from job completion to next loop
scheduling in the NFT bidding bot server. The flow involves:

- Job completion tracking via distributed Redis locks
- Progress calculation and completion detection
- Timer management for scheduling next loops
- State persistence to Redis for recovery

Key Files:
- bidding-bot-server/src/index.ts (main logic)
- bidding-bot-server/src/utils/lock.ts (DistributedLockManager)
- bidding-bot-server/src/utils/redis.ts (Redis client)

3.1 markJobAsProcessed()
--------------------------------------------------------------------------------
Location: Lines 4766-4997

Purpose:
  Entry point when a job completes. Increments the completed jobs counter
  using a distributed lock to prevent race conditions between workers.

Parameters:
  - taskId: string - Unique task identifier
  - marketplace: string - 'opensea' | 'blur' | 'magiceden'
  - parentJobId: string - Parent job identifier for grouping

Flow:
  1. Constructs lock key for this task/marketplace/parent combination
  2. Acquires distributed Redis lock (5s TTL, 3 retries)
  3. Fetches current counter: task:{taskId}:{marketplace}:parent:{parentJobId}
  4. Increments completedJobs
  5. Validates: completedJobs <= totalJobs
  6. Stores updated counter in Redis
  7. Releases lock
  8. Calls updateTaskRunningPercentage()

Locking:
  - Type: Distributed (Redis via DistributedLockManager)
  - TTL: 5 seconds
  - Retry: 3 attempts with exponential backoff
  - Key format: task:{taskId}:mp:{marketplace}:parent:{parentJobId}:lock

Error Handling:
  - Lock acquisition failure: Schedules retry in 1 second
  - Counter overflow: Caps at totalJobs with warning log

Redis Keys Used:
  - task:{taskId}:{marketplace}:parent:{parentJobId} (counter object)
  - task:{taskId}:mp:{marketplace}:parent:{parentJobId}:lock (lock)

--------------------------------------------------------------------------------
3.2 updateTaskRunningPercentage()
--------------------------------------------------------------------------------
Location: Lines 4332-4589

Purpose:
  Calculates completion percentages and detects when a marketplace has
  finished processing all jobs, triggering the next loop scheduling.

Parameters:
  - taskId: string - Unique task identifier
  - marketplace: string - 'opensea' | 'blur' | 'magiceden'

Flow:
  1. Retrieves task configuration from tasksById
  2. Scans Redis for all parent job counters
  3. Aggregates completedJobs and totalJobs across parent jobs
  4. Calculates percentage: (completed / total) * 100
  5. Stores in mpCompletionStats[taskId][marketplace]
  6. Checks: mpCompleted >= mpTotal
  7. If complete: Fires checkTaskCompletionAndScheduleNext() WITHOUT AWAIT
  8. Updates overall task completion percentage

Completion Detection:
  - Condition: completedJobs >= totalJobs for marketplace
  - Action: Fire-and-forget call to checkTaskCompletionAndScheduleNext()

Stuck State Detection:
  - Monitors for tasks stuck at partial completion
  - Logs warning if stuck for extended period

Redis Keys Scanned:
  - Pattern: task:{taskId}:{marketplace}:parent:*
  - Type: Hash objects with completedJobs/totalJobs

Critical Issue:
  ⚠️ Line 4484: checkTaskCompletionAndScheduleNext() called WITHOUT await
  This means errors are silently swallowed and race conditions possible.

3.3 checkTaskCompletionAndScheduleNext()
--------------------------------------------------------------------------------
Location: Lines 4616-4732

Purpose:
  Sets the task status to COMPLETED and schedules the next loop iteration.
  Uses in-memory lock to prevent duplicate scheduling.

Parameters:
  - taskId: string - Unique task identifier
  - marketplace: string - 'opensea' | 'blur' | 'magiceden'
  - reason: string - Why completion was triggered

Flow:
  1. Checks if taskId already in tasksInCompletionProcess Set
  2. If yes: Returns immediately (prevents duplicates)
  3. Adds taskId to tasksInCompletionProcess
  4. Sets task status to COMPLETED
  5. Updates processedAt timestamp
  6. Waits 500ms (allow status to propagate)
  7. Calls scheduleNextLoop()
  8. Waits 100ms
  9. Clears parent job data from memory
  10. Removes taskId from tasksInCompletionProcess

Locking:
  - Type: In-memory (JavaScript Set)
  - Lock: tasksInCompletionProcess.add(taskId)
  - Release: tasksInCompletionProcess.delete(taskId)

Memory Cleanup:
  - Clears: parentJobCompletedJobs[taskId]
  - Clears: parentJobTotalJobs[taskId]
  - Clears: parentJobStatus[taskId]

Timing Delays:
  - 500ms after setting COMPLETED (status propagation)
  - 100ms after scheduleNextLoop() (cleanup buffer)

--------------------------------------------------------------------------------
3.4 scheduleNextLoop()
--------------------------------------------------------------------------------
Location: Lines 5068-5393

Purpose:
  Creates timers to schedule the next loop iteration after a delay.
  Manages countdown display and ensures only one timer fires.

Parameters:
  - taskId: string - Unique task identifier
  - marketplace: string - 'opensea' | 'blur' | 'magiceden'
  - options?: { skipLog?: boolean }

Flow:
  1. Retrieves task configuration (loopInterval)
  2. Validates task is still active
  3. Increments loop counter: loopCounterStats[taskId][marketplace]++
  4. Sets task status to SCHEDULED
  5. Clears any existing timers for this task
  6. Creates countdown interval (1 second)
  7. Creates main timeout (loopInterval * 1000ms)
  8. On timeout fire:
     a. Acquires loopSchedulingLock (via Map)
     b. Clears countdown interval
     c. Validates task still active
     d. Releases lock
     e. Calls startTask()
  9. Stores timer references in taskTimers Map
  10. Persists task state to Redis

Timer Management:
  - Countdown interval: Logs "Next loop in X seconds" every second
  - Main timeout: Fires when loopInterval expires
  - Storage: taskTimers Map<taskId, { timeout, interval }>

Locking (Timer Execution):
  - Type: Synchronous (JavaScript Map)
  - Lock: loopSchedulingLock.set(taskId, { timestamp, marketplace })
  - Stale detection: 5 minutes
  - Release: loopSchedulingLock.delete(taskId)

Loop Counter:
  ⚠️ Line 5115: loopCounterStats[taskId][marketplace]++
  NOT protected by any lock - potential race condition

Redis Persistence:
  - Stores: taskId, marketplace, loopCounter, scheduledAt, loopInterval
  - Key: scheduled:task:{taskId}:{marketplace}
  - Fire-and-forget (errors logged but not awaited)

                       4. CRITICAL ISSUES IDENTIFIED
================================================================================

--------------------------------------------------------------------------------
HIGH SEVERITY
--------------------------------------------------------------------------------

Issue #1: Missing await on line 4484
  Location: updateTaskRunningPercentage(), line 4484
  Code: checkTaskCompletionAndScheduleNext(taskId, marketplace, reason)
  Problem:
    - Called without await
    - Errors silently swallowed
    - Race condition if multiple jobs complete rapidly
    - No error propagation to caller
  Impact:
    - Next loop may not schedule if error occurs
    - Silent failures difficult to debug
    - Task may appear "stuck" with no logs
  Fix: Add await before the call

--------------------------------------------------------------------------------
MEDIUM SEVERITY
--------------------------------------------------------------------------------

Issue #2: Loop counter not locked
  Location: scheduleNextLoop(), line 5115
  Code: loopCounterStats[taskId][marketplace]++
  Problem:
    - No lock protection
    - Multiple concurrent calls could corrupt counter
  Impact:
    - Loop count may be inaccurate
    - Debug logs may show wrong loop number
  Fix: Add synchronization or atomic increment

Issue #3: Fire-and-forget job retry
  Location: markJobAsProcessed(), lines 4909-4914
  Code: setTimeout(() => markJobAsProcessed(...), 1000)
  Problem:
    - Lock failure schedules retry but returns immediately
    - Retry failures silently ignored
    - No retry count limit
  Impact:
    - Infinite retry loop possible
    - No visibility into retry attempts
  Fix: Add retry tracking and limit

Issue #4: Lock TTL timeout risk
  Location: markJobAsProcessed(), lines 4888-4893
  Code: DistributedLockManager with 5s TTL
  Problem:
    - If operation takes longer than 5 seconds, lock expires
    - Another worker could acquire lock mid-operation
  Impact:
    - Race condition on counter increment
    - Potential double counting
  Fix: Extend TTL during operation or use shorter critical section

Issue #5: Race between status and timer
  Location: scheduleNextLoop(), lines 5129-5138
  Problem:
    - Task could be deactivated between:
      a. Setting status to SCHEDULED
      b. Creating the timeout
    - Timer could fire for deactivated task
  Impact:
    - Orphaned timer execution
    - Task starts after deactivation
  Fix: Atomic status + timer creation or recheck in timeout

--------------------------------------------------------------------------------
LOW SEVERITY
--------------------------------------------------------------------------------

Issue #6: Countdown timer overhead
  Location: scheduleNextLoop(), lines 5175-5210
  Problem:
    - 1-second interval fires 86,400 times/day per task
    - No early termination when task deactivates
  Impact:
    - Unnecessary CPU cycles
    - Memory pressure from interval closures
  Fix: Use larger interval or lazy countdown

Issue #7: Redis fire-and-forget persistence
  Location: persistTaskState(), lines 5365-5378
  Problem:
    - Uses .catch() instead of await
    - Errors logged but not handled
  Impact:
    - Task state may not persist
    - Crash recovery may fail
  Fix: Await or implement retry logic
